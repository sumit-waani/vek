# vekd daemon: SQLite state, master key crypto, process supervisor, and htmx dashboard

This change implements the vekd binary from scratch — a production deployment supervisor for vek applications, managed entirely through a web dashboard on port 8080. The implementation covers database schema and CRUD (SQLite with WAL), master key generation and XOR-stream encryption of secrets, a fork/exec process supervisor with restart-on-crash logic, and a full htmx-based admin dashboard with session-cookie auth, app lifecycle management, env vars, log tailing, and settings pages. The existing HTTP server (epoll event loop, router, parser) is reused directly. Documentation was updated to remove the previously-planned CLI interface.

Watch for: password hashing uses unsalted single-pass SHA-256 (confirmed) — trivially rainbow-tabled and must be replaced before production exposure. The encryption scheme lacks a nonce/IV, meaning identical plaintexts produce identical ciphertexts under the same key (confirmed). Session cookies omit the `Secure` flag (confirmed), which allows credential theft over the plaintext HTTP transport this service currently listens on. The `next_port` counter lives only in memory and resets on restart, risking port collisions with already-assigned apps (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The encryption layer uses SHA-256 in counter mode as a stream cipher keyed by the master key. Because the counter always starts at zero and there is no per-message nonce, encrypting the same secret twice produces the same ciphertext. An attacker with DB read access can identify duplicate values across apps and perform crib-dragging. More critically, the password hashing is raw SHA-256 with no salt, making offline cracking nearly instantaneous on modern hardware.

Session management is an in-memory fixed-array store of 64 slots with LRU eviction. Sessions survive only until the daemon restarts; after that all users are logged out. The cookie is `HttpOnly; SameSite=Strict` but lacks the `Secure` directive — acceptable only if TLS is guaranteed by a reverse proxy, which is not enforced or documented anywhere.

The first-login flow auto-creates an admin account for whatever credentials are posted when the user table is empty. This is a race condition: two concurrent requests from different origins can both observe `user_count == 0` and both create admin accounts, giving the second requester admin access.

Port assignment for apps is derived from `ctx->next_port`, an integer that starts at 10000 on every boot. Existing apps already bound to ports in that range will collide on the next create. The port should be derived from the database (MAX port + 1, or a free-list query) rather than an in-memory counter.

The supervisor forks processes and monitors them via periodic `waitpid(WNOHANG)`, but nothing in the current code calls `vekd_supervisor_check` periodically — the event loop blocks in epoll and there's no timer or SIGCHLD handler wired to trigger the reap/restart cycle.

<summary>Issues (8)</summary>

1. **Unsalted SHA-256 password hashing** — Replace `hash_password` with bcrypt, scrypt, or argon2. Single-pass unsalted SHA-256 provides no brute-force resistance.
2. **Deterministic encryption (no nonce/IV)** — Prepend a random nonce to each encrypted value and include it in the SHA-256 counter-mode input so identical plaintexts produce different ciphertexts.
3. **Admin account creation race** — Wrap the "check count then insert" logic in a transaction with a unique constraint check, or use INSERT-if-empty SQL to prevent concurrent first-login races.
4. **Port counter resets on restart** — Derive `next_port` from `SELECT MAX(port) + 1 FROM apps` at startup instead of the compile-time constant.
5. **Session cookie missing Secure flag** — Add `Secure` to `vekd_session_format_cookie` and document that TLS termination (reverse proxy or built-in) is required.
6. **Supervisor check never called** — Wire `vekd_supervisor_check` into the event loop (timer fd, SIGCHLD self-pipe, or periodic epoll timeout) so crashed children are actually reaped and restarted.
7. **App deletion leaves orphan env_vars, events, releases** — Add cascading DELETEs or `ON DELETE CASCADE` to the foreign keys so deleting an app cleans up related rows.
8. **htmx loaded from unpkg CDN** — The dashboard depends on a third-party CDN at runtime. For a single-binary deployment story, vendor the htmx JS or inline it in the template.

## Crypto: XOR stream without nonce

The cipher in `vekd_crypto_encrypt` expands the master key into a keystream via `SHA256(key || counter)` where counter starts at zero for every call. Two encryptions of the same plaintext yield byte-for-byte identical ciphertext. For env vars (where the same value like `"true"` or a shared database URL appears across apps) this leaks equality. The fix is straightforward: generate 16 random bytes as a nonce, prepend it to the ciphertext, and feed `SHA256(key || nonce || counter)`. Decryption reads the nonce prefix before producing the keystream.

The scheme also provides no authentication (no HMAC/tag), so ciphertext is malleable — an attacker who can write to the SQLite file can flip bits in encrypted values and the system will happily decrypt garbage. Adding an HMAC-SHA256 tag over the ciphertext would prevent this.

```c
// Current (vekd_crypto.c:83-84)
block_input[VEKD_KEY_SIZE]     = (uint8_t)(counter >> 24);
block_input[VEKD_KEY_SIZE + 1] = (uint8_t)(counter >> 16);
```

No nonce field exists anywhere in the block_input — just key + 4-byte counter.

## Password hashing and first-login race

`hash_password` in `vekd_web.c` calls `sha256_compute` directly on the password bytes:

```c
static void hash_password(const char *password, char *out_hash, size_t hash_len) {
    uint8_t digest[32];
    sha256_compute((const uint8_t *)password, strlen(password), digest);
    ...
}
```

No salt, no iteration count. This gives zero defense against precomputed tables or GPU-parallelized cracking. A migration to bcrypt (or even PBKDF2-SHA256 with a per-user salt stored in the `users` row) is needed before this is exposed on a public interface.

The first-login path in `handle_login_post`:

```c
int user_count = vekd_db_user_count(ctx->db);
if (user_count == 0) {
    char pw_hash[128];
    hash_password(password, pw_hash, sizeof(pw_hash));
    vekd_db_user_create(ctx->db, email, pw_hash, 1);
}
```

There's a TOCTOU window between checking the count and inserting. Two concurrent POST requests can both see count=0 and both succeed (SQLite's email UNIQUE won't help if they use different emails). Wrapping this in `BEGIN IMMEDIATE` or using `INSERT INTO users ... SELECT ... WHERE (SELECT COUNT(*) FROM users) = 0` makes it atomic.

## Port assignment and state loss on restart

```c
// vekd_web.h
typedef struct {
    ...
    int next_port;  /* Next port to assign to an app */
} VekdWebContext;
```

Initialized to `VEKD_APP_PORT_MIN` (10000) in `vekd_web_init`. If 5 apps already exist in the DB from a prior run, the next boot will assign port 10000 again. The schema has a UNIQUE constraint on `apps.port`, so the INSERT will fail, but the user will just see "Failed to create app" with no clear reason. The counter should query `SELECT COALESCE(MAX(port), 9999) + 1 FROM apps` on init.

## Supervisor reap/restart cycle disconnected from event loop

`vekd_supervisor_check` performs non-blocking `waitpid` to detect exited children and restart them. But `vekd_main.c` calls `http_server_start` which blocks inside epoll — nothing ever calls `vekd_supervisor_check`. Crashed child processes will remain zombies until the daemon itself exits.

Options: (a) register a `timerfd` in the epoll loop that fires every second and calls `vekd_supervisor_check`, (b) install a `SIGCHLD` handler that writes to a self-pipe monitored by epoll, or (c) spawn a dedicated monitoring thread. Without one of these, the auto-restart claim in the docs is inoperative.

## Cascading deletes missing

`vekd_db_app_delete` removes only the `apps` row. The schema uses `REFERENCES apps(id)` but `PRAGMA foreign_keys=ON` only enforces constraints — it doesn't cascade deletes by default. Orphan rows accumulate in `env_vars`, `events`, and `releases` after app deletion. Either add `ON DELETE CASCADE` to the FK definitions or add explicit DELETE statements in `vekd_db_app_delete`.

## Session lifetime and transport

Sessions are purely in-memory (`VekdSessionStore` is a stack-allocated struct in `main`). A daemon restart logs out all users. For a single-server deployment this is tolerable but worth documenting.

The `Set-Cookie` format:

```c
"session=%s; Path=/; HttpOnly; SameSite=Strict"
```

Missing `Secure`. Since vekd currently serves plain HTTP on 8080, a network-positioned attacker can sniff the session token. The intended deployment presumably puts Cloudflare or nginx in front with TLS, but that assumption isn't enforced. At minimum, document it; ideally, add `Secure` and refuse to start without `--behind-proxy` or `--tls-cert` flags.

## Test coverage gaps

The test file `test_vekd_db.c` covers schema creation, app CRUD, release creation, events, users, and the crypto encrypt/decrypt round-trip (16 tests total). Not tested:

- Session management (create, validate, expire, evict)
- Web handler logic (login flow, auth check, form parsing, redirect behavior)
- Supervisor start/stop/restart logic (would require fork in test harness)
- The port-collision scenario
- The first-login race condition
- Encryption of empty input or very large input (only 20 and 100 bytes tested)
- Form parsing edge cases (malformed bodies, missing terminators)
