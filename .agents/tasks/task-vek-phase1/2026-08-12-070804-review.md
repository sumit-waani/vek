# Stack-based VM and single-pass compiler for the vek language (v2)

Phase 1 delivers a complete language pipeline: lexer, single-pass Pratt compiler, NaN-boxed stack VM with computed GOTO dispatch, mark-and-sweep GC, and built-in type methods for strings, lists, and maps. The previous review surfaced seven issues (GC tracing gaps, map tombstones, stack overflow, shift UB, recursion depth); all seven have been addressed in commit `261d59b`. The fixes are correct in isolation, but two of them are incomplete, and one pre-existing bug in a sibling data structure now stands out by contrast.

Watch for: `vm_push` overflow guard sets `had_error` and returns without halting the dispatch loop — execution continues silently with a corrupted stack (confirmed). `intern_table_remove_unmarked` NULLs entries without a tombstone, breaking probe chains in the intern table — the same class of bug that was just fixed in `ObjMap` (confirmed). `string_replace_method` computes buffer size using unsigned subtraction that wraps to a massive value when the replacement is shorter than the target (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The stack overflow fix in `vm_push` introduces a bounds check that prevents the write, but the caller (the dispatch loop) never inspects `vm.had_error` after pushing. The function returns normally, the push is silently dropped, and the next opcode operates on stale stack values. In practice this means a stack overflow doesn't crash but produces garbage results or triggers a type error deeper in execution.

The intern table uses the same open-addressing/linear-probing scheme as `ObjMap`, but `intern_table_remove_unmarked` still NULLs entries without a tombstone — the exact pattern that was fixed for the map. After a GC sweep removes some interned strings, subsequent `intern_table_find` calls will stop probing at the resulting holes and fail to find strings stored past the deleted slot. The consequence is duplicate string allocations and broken identity comparisons (since the VM relies on interned pointer equality for string matching).

`string_replace_method` computes `new_len = str->length + count * (new_str->length - old->length)` where all values are `uint32_t`. When the replacement is shorter than the target, `(new_str->length - old->length)` wraps to ~4 billion, producing a massive `malloc`. On systems that succeed (overcommit), the subsequent `memcpy` reads garbage; on systems that fail, `malloc` returns NULL and `memcpy` through NULL is UB. A simple `"hello".replace("llo", "")` triggers this.

## vm_push overflow guard doesn't halt execution

The fix adds:

```c
void vm_push(Value value) {
    if (vm.stack_top >= vm.stack + STACK_MAX) {
        fprintf(stderr, "Runtime error: Stack overflow.\n");
        vm.had_error = true;
        return;
    }
    *vm.stack_top = value;
    vm.stack_top++;
}
```

Every call site in the dispatch loop follows the pattern:

```c
    vm_push(constant);
    DISPATCH();
```

There is no check for `vm.had_error` between the push and the next dispatch. After overflow, `stack_top` stays at its maximum position, the value is silently dropped, and the next `vm_pop()` will decrement `stack_top` and read whatever was already there — producing a type mismatch or corrupted value downstream.

The cleanest fix: make `vm_push` signal the error through the same mechanism as `runtime_error` + `return INTERPRET_RUNTIME_ERROR`. Since `vm_push` is called from a non-`InterpretResult`-returning context in some places (native functions, `vm_interpret` setup), the path of least resistance is to check `vm.had_error` at the top of `DISPATCH()` or use `setjmp/longjmp` for fatal errors.

## Intern table probe chain corruption after GC sweep

`intern_table_remove_unmarked` iterates the table and NULLs any entry whose object is unmarked:

```c
void intern_table_remove_unmarked(void) {
    for (uint32_t i = 0; i < intern_table.capacity; i++) {
        ObjString* entry = intern_table.entries[i];
        if (entry != NULL && !(entry->header.flags & OBJ_FLAG_MARK)) {
            intern_table.entries[i] = NULL;
            intern_table.count--;
        }
    }
}
```

`intern_table_find` terminates probing when it encounters NULL:

```c
if (entry == NULL) {
    return NULL;
}
```

If string A and string B hash to the same bucket, with A stored at index `i` and B at `i+1`, sweeping A makes B permanently unreachable through `intern_table_find`. The next `obj_string_new` for B's content will allocate a duplicate string object. Since the VM uses pointer identity for interned string comparison (e.g., map key lookup via `entry->key == key`), the duplicate will fail to match the original, causing silent data loss in maps.

The fix mirrors what was done for `ObjMap`: either use a tombstone sentinel that `intern_table_find` skips over but `intern_table_insert` can reuse, or rebuild/compact the table after sweeping.

## Unsigned arithmetic overflow in string_replace_method

```c
uint32_t new_len = str->length + (uint32_t)count * (new_str->length - old->length);
```

When `new_str->length` (e.g., 0 for an empty replacement) is less than `old->length` (e.g., 3), the subtraction `0 - 3` wraps to `0xFFFFFFFD` in unsigned 32-bit arithmetic. Multiplied by `count`, the result is a huge `new_len`, leading to `malloc(new_len + 1)` attempting a multi-gigabyte allocation.

Fix: compute the difference in signed arithmetic:

```c
int64_t delta = (int64_t)new_str->length - (int64_t)old->length;
int64_t new_len_s = (int64_t)str->length + (int64_t)count * delta;
if (new_len_s < 0) new_len_s = 0; // safety
uint32_t new_len = (uint32_t)new_len_s;
```
