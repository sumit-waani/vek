# Stack-based VM and single-pass compiler for the vek language (v3 — final pass)

All ten issues raised across v1 and v2 have been resolved. The `DISPATCH` macro now checks `vm.had_error` before fetching the next opcode, halting execution immediately after a stack overflow. The intern table uses a tombstone sentinel (`INTERN_TOMBSTONE`) that preserves probe chains across GC sweeps. `string_replace_method` computes buffer size with signed `int64_t` arithmetic, eliminating the unsigned wrap for shorter replacements. Build is clean (modulo expected computed-GOTO extension warnings), 99 unit tests and 8 integration tests pass.

Watch for: GC never fires during normal execution — `gc_maybe_collect` is only reachable through `heap_alloc`, which nothing calls — and `gc_mark_roots` does not scan the VM stack or call frames. This is a dormant correctness gap: harmless today, but the moment someone wires collection into `vek_alloc` (as the architecture doc implies), every stack-held object becomes collectible mid-execution (likely).

**Verdict**: APPROVED

## High-level view

The three v2 fixes are structurally sound. `vm_push` overflow terminates via the `DISPATCH` macro's `had_error` check — every opcode that pushes goes through DISPATCH before the next read, so no stale-stack execution is possible. The intern table tombstone mirrors the map's pattern: `find` skips tombstones, `insert` reuses them, `remove_unmarked` places them, and `grow` rehashes without them. The signed-arithmetic fix in `string_replace` computes the delta as `int64_t` before multiplying by occurrence count, with a floor at zero.

The GC subsystem is tested via explicit `gc_collect()` calls but never triggers automatically during execution — all object allocation goes through `vek_alloc` (plain `malloc`), not the `heap_alloc` path that calls `gc_maybe_collect`. Additionally, `gc_mark_roots` only visits pinned objects and the explicit root stack; it does not scan `vm.stack[0..stack_top]` or the closures in `vm.frames[]`. These two gaps are mutually masking: since GC never fires mid-execution, the missing stack scan doesn't manifest. Both will need fixing together when automatic collection is enabled.

## GC trigger path is disconnected from the allocation path

`alloc_object` (the sole constructor for heap objects) calls `vek_alloc`, which is plain `malloc` with bookkeeping. `gc_maybe_collect` exists only in `heap_alloc`, which no production code calls. The page-based allocator appears to be scaffolding for a future bump-allocation optimization.

When automatic collection is eventually enabled, `gc_mark_roots` will need to walk:

- The value stack: `for (Value* slot = vm.stack; slot < vm.stack_top; slot++) gc_mark_value(*slot);`
- Call frame closures: `for (int i = 0; i < vm.frame_count; i++) gc_mark_object((ObjHeader*)vm.frames[i].closure);`
- Open upvalues: `for (ObjUpvalue* uv = vm.open_upvalues; uv != NULL; uv = uv->next) gc_mark_object((ObjHeader*)uv);`

Without these, any GC cycle mid-execution would collect strings, lists, closures, and maps that are live on the stack but not pinned or explicitly rooted.

## Intern table probe termination safety

The intern table's `intern_table_find` terminates only on NULL (tombstones are skipped). The 75% load factor threshold governs live entries, and tombstones are created exclusively from previously-live slots during GC sweeps. The NULL slots that constitute the original 25% headroom are never overwritten with tombstones — guaranteeing that `find` always reaches a NULL and terminates, even after repeated sweep cycles.
