# Stack-based VM and single-pass compiler for the vek language

Phase 1 delivers a complete language pipeline from source to execution: lexer, single-pass Pratt compiler, NaN-boxed stack VM with computed GOTO dispatch, mark-and-sweep GC, and a collection of built-in types (strings, lists, maps) with method dispatch. The language surface is Ruby/Elixir-inspired (`end`-terminated blocks, newline-as-terminator, `fn`/`if`/`while`/`for..in`). The build is clean (-Wpedantic, all warnings are the expected GNU label-as-value extension), all 99 unit tests and 8 integration tests pass.

Watch for: The GC does not trace through `ObjFunction` constants, `ObjUpvalue` closed values, or `ObjBoundMethod` receivers (confirmed) — any program that triggers collection while closures, closed-over values, or bound methods are live will see use-after-free or silent data corruption. Map deletion breaks linear probing chains (confirmed), causing lookups to miss existing keys after a delete. `vm_push` has no stack overflow guard, so a deeply nested expression or long argument list will write past `stack[STACK_MAX]` without detection.

**Verdict**: NEEDS_CHANGES

## High-level view

The GC's mark phase has three incomplete `case` branches that silently skip tracing. `OBJ_FUNCTION` is labeled "leaf" but holds a `name` string pointer and a constant pool full of `Value`s that may reference heap objects. `OBJ_UPVALUE` and `OBJ_BOUND_METHOD` have empty trace handlers despite owning heap references. Under any non-trivial GC pressure, live objects reachable only through these paths will be swept.

The open-addressing map uses linear probing for both insert and lookup, terminating at a NULL key. `obj_map_delete` sets the key to NULL without a tombstone sentinel, so any key stored past the deleted slot in the same probe chain becomes permanently unreachable via `obj_map_get`.

The VM stack is a fixed 65536-slot array. `vm_push` writes unconditionally at `*stack_top++` without checking bounds. Stack overflow from deeply recursive expressions, large list literals, or deep call chains (beyond the 256-frame check) results in undefined behavior rather than a runtime error.

Integer arithmetic on 48-bit NaN-boxed ints silently wraps on overflow. The `INT_VAL` macro masks to 48 bits, so adding two large 47-bit numbers produces a garbage value. This is arguably acceptable as a known limitation for phase 1, but it's undocumented.

## GC tracing gaps in ObjFunction, ObjUpvalue, and ObjBoundMethod

The `gc_trace_object` switch has:

```c
case OBJ_STRING:
case OBJ_BYTES:
case OBJ_FUNCTION:
    // Leaf objects: no outgoing heap references
    break;
```

`ObjFunction` is not a leaf. It owns `ObjString* name` and a `Chunk` containing `Value* constants` — the constant pool holds string literals, nested function references, and any other heap-allocated constants emitted by the compiler. If a GC cycle runs while a function is reachable only through a closure (which does trace the function header but relies on the function's own trace to follow its internals), every constant in that function's pool is subject to sweep.

The upvalue case:

```c
case OBJ_UPVALUE: {
    // Mark the closed-over value
    // We need to include vm.h for this but ObjUpvalue is defined there.
    // For now, the upvalue's closed value is marked via its Value stored in closure.
    break;
}
```

The comment's assumption is incorrect. When an upvalue closes, `upvalue->location` points to `&upvalue->closed`. The closure stores a `Value` that is a pointer to the `ObjUpvalue` itself — it does not store the closed value directly. After tracing the closure, the GC marks the `ObjUpvalue` header but never follows `upvalue->closed`, which could be any heap-allocated value (a string, list, map, another closure).

`OBJ_BOUND_METHOD` similarly holds a `Value receiver` that is never traced. If the receiver is the sole remaining reference to an object (common with method chaining), it will be collected.

## Map deletion breaks linear probing

The comment on `obj_map_delete` says "uses tombstone approach" but the implementation just sets `entry->key = NULL` and decrements length. In an open-addressing table with linear probing, `obj_map_get` terminates its probe loop when it encounters a NULL key:

```c
if (entry->key == NULL) {
    return false;  // stop probing
}
```

If keys A, B, C hash to the same bucket and are stored in consecutive slots, deleting B makes C permanently unreachable because the probe for C stops at the now-empty B slot. The fix is either a dedicated tombstone pointer (e.g., a static sentinel `ObjString*`) that `obj_map_get` treats as "continue probing" while `obj_map_set` treats as "available for insertion", or a rehash of the probe cluster on delete.

## Stack overflow in vm_push

```c
void vm_push(Value value) {
    *vm.stack_top = value;
    vm.stack_top++;
}
```

No bounds check. The stack is `Value stack[STACK_MAX]` (65536 slots). While call depth is capped at `FRAMES_MAX` (256), the stack can overflow independently — a single call with many temporaries or a list literal with >65536 elements will write past the end of the array. Add:

```c
if (vm.stack_top >= vm.stack + STACK_MAX) {
    runtime_error("Stack overflow.");
    // ... handle error return
}
```

## Undefined behavior in shift operations

`OP_SHL` and `OP_SHR` extract the shift count as an `int64_t` and pass it directly to `<<` / `>>`:

```c
vm_push(INT_VAL(AS_INT(a) << AS_INT(b)));
```

If `AS_INT(b)` is negative or >= 64, this is undefined behavior per C11 6.5.7. A user writing `1 << 100` or `1 << -1` triggers UB at the C level. Either clamp the shift to 0..63 or emit a runtime error.

## Integer overflow in arithmetic

`INT_VAL` masks the result to 48 bits:

```c
return TAG_INT | ((uint64_t)i & PAYLOAD_MASK);
```

This means `AS_INT(a) + AS_INT(b)` produces a full 64-bit sum, which is then silently truncated to 48 bits by `INT_VAL`. Two 47-bit-max values summing to 48+ bits produce garbage. The design doc specifies 48-bit signed ints, so this is technically "correct" (wrapping semantics), but it's a sharp edge that could surprise users. Consider at minimum documenting the range `[-2^47, 2^47 - 1]` in the language spec.

## Test coverage

Unit tests cover NaN-boxing roundtrips, lexer tokens, compiler output for key constructs, object CRUD operations, and basic GC mark/sweep. Integration tests exercise arithmetic, strings, collections, control flow, closures, and error paths.

Not tested: GC collection under allocation pressure during execution (the GC tests use manually pinned/rooted objects without running the VM), map delete followed by lookup of a colliding key, stack overflow conditions, large integer edge cases, deeply nested closures with multiple upvalue capture levels, or iteration over maps that are mutated during iteration.
