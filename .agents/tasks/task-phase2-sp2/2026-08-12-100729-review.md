# Web framework stdlib: database, views, sessions, forms, routing

Four new stdlib packages (db, html, session/csrf/form, pages) bring Vek from a language with an HTTP server to something approaching a web framework. The db package wraps SQLite with parameterized queries. The html package implements a builder-based DSL with auto-escaping. Session management uses HMAC-SHA256 signed cookies with a custom SHA-256 and base64 implementation. Form parsing handles URL-encoded bodies with declarative validation rules. The pages package provides file-based routing by scanning a directory tree and compiling `.ve` files on the fly.

Watch for: pinned objects are never unpinned on replacement, leaking memory across requests (confirmed). The CSRF length-check short-circuit before constant-time comparison leaks token length via timing (confirmed). The `build_row_map` helper in the db package doesn't root the key ObjString before allocating the value — currently harmless because `vek_alloc` doesn't trigger GC, but a latent use-after-free if the allocator changes (likely). Global mutable state in every package (db connection, session map, form state, builder stack) makes concurrent or pipelined request handling impossible without a redesign (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The db package exposes a single global `sqlite3*` connection with prepared-statement parameterized queries. The global connection design is fine for a single-threaded event loop, but `db.open` silently closes any existing connection — a footgun for library code that doesn't expect the connection to be yanked out.

The html package uses a static array of `Builder` structs as a stack (max depth 32) to support nested `render_inline` calls. Auto-escaping covers the five critical characters (`& < > " '`). If nesting exceeds 32, `builder_push` returns NULL and tag helpers silently produce no output — no error reaches the user.

The CSRF validation short-circuits on length mismatch before reaching the constant-time XOR loop, leaking whether the submitted token has the correct length. The session `decode` path pins a new map without unpinning the old one, creating an ever-growing set of pinned (uncollectable) objects.

Form parsing and validation pin new maps on every call without unpinning the previous ones — same leak pattern as session. The `required` rule check calls `AS_BOOL` without verifying the value is actually a boolean, which will misinterpret arbitrary values.

The pages package recursively scans a directory, compiles each `.ve` file into a closure, and executes it. There's no cycle detection or depth limit on the directory walk, so a symlink loop will stack-overflow the process.

<summary>Issues (8)</summary>

1. **Pin leak in session.decode** — `session_data` is replaced with a new pinned map but the old map is never unpinned. Call `vm_unpin` on the previous `session_data` before reassigning. Same pattern in `form.parse` and `form.validate`.
2. **Pin leak in form.parse / form.validate** — `form_parsed` and `form_error_list` are pinned on every call without unpinning the previous allocation. Unpin before reassigning.
3. **CSRF timing leak on token length** — `native_csrf_validate` returns early if `provided->length != stored_str->length`, revealing whether the attacker's token is the right length. Since tokens are always 64 hex chars, normalize both to 64 before comparing (or always compare up to 64 bytes).
4. **Unrooted key in build_row_map** — The `ObjString* key` returned by `obj_string_new` is not GC-rooted before `read_column` allocates another object. Currently safe because `alloc_object` uses `vek_alloc` (no GC trigger), but becomes a use-after-free if allocation strategy changes. Root the key or restructure.
5. **AS_BOOL without IS_BOOL guard in form.validate** — The `required` rule fetches a Value and calls `AS_BOOL(req_val)` without checking `IS_BOOL(req_val)`. A truthy non-boolean value (like an integer or string) will be reinterpreted as a raw bit pattern.
6. **Session secret not zeroed on free** — `native_session_init` frees the old secret with plain `free()`. The old key material remains in freed memory. Use `memset` before free (or `explicit_bzero` where available).
7. **Unbounded directory recursion in pages.scan** — A symlink loop or deeply nested directory tree will cause stack overflow. Add a depth limit parameter or symlink detection.
8. **Global mutable state prevents request isolation** — `session_data`, `flash_data`, `form_parsed`, `form_error_list`, `db_conn`, and `builder_stack` are all process-global statics. Any future concurrency (even cooperative, e.g., handling a second request while the first awaits I/O) will corrupt state. Document this as a known single-request-at-a-time constraint or move to per-request context objects.

## Pin/unpin lifecycle across packages

Three packages exhibit the same defect: they call `vm_pin` on a newly allocated map or list, then later replace the static pointer without calling `vm_unpin` on the previous object.

In `stdlib_session.c`, `session.decode` at line 644:
```c
// Replace session data
session_data = new_data;
vm_pin((ObjHeader*)session_data);
```
The old `session_data` (pinned in `ensure_session_data` or a prior `decode`) remains permanently pinned.

In `stdlib_form.c`, `form.parse` at line 153:
```c
ObjMap* parsed = parse_form_body(body->data, body->length);
vm_pin((ObjHeader*)parsed);
form_parsed = parsed;
```
And `form.validate` at lines 169-170:
```c
form_error_list = obj_list_new();
vm_pin((ObjHeader*)form_error_list);
form_is_valid = true;
form_parsed = data;
vm_pin((ObjHeader*)form_parsed);
```

In a web server handling requests, this is a steady memory leak — every form submission pins a new map that can never be collected.

Fix: before each reassignment, check if the static pointer is non-NULL and call `vm_unpin` on it.

## CSRF constant-time comparison defeated by length check

```c
if (provided->length != stored_str->length) return BOOL_VAL(false);
```

This exits before the constant-time XOR loop. An attacker who controls the submitted token can binary-search for the correct length by measuring response time. Since CSRF tokens are always 64 hex characters (generated by `native_csrf_generate`), this is low-severity in practice — an attacker who already knows the format knows the length. But if token generation ever changes (e.g., variable-length), this becomes exploitable. The idiomatic fix is to always compare exactly 64 bytes, treating shorter inputs as padded with a sentinel.

## Unrooted ObjString key in build_row_map

```c
const char* col_name = sqlite3_column_name(stmt, i);
ObjString* key = obj_string_new(col_name, (uint32_t)strlen(col_name));
Value val = read_column(stmt, i);  // can allocate ObjString or ObjBytes
gc_push_root(val);
obj_map_set(map, key, val);
gc_pop_root();
```

Between creating `key` and using it in `obj_map_set`, the call to `read_column` invokes `obj_string_new` or `obj_bytes_new`. These go through `alloc_object → vek_alloc → malloc`, which does not call `gc_maybe_collect`. If a future refactor routes allocation through `heap_alloc` (which does trigger GC), `key` would be swept before `obj_map_set` uses it.

The same pattern exists in `parse_form_body`:
```c
ObjString* key = obj_string_new(key_buf, (uint32_t)key_len);
free(key_buf);
Value value = OBJ_VAL(obj_string_new("", 0));  // allocates, key unrooted
```

## AS_BOOL without type check in form validation

```c
Value req_val;
if (obj_map_get(rule, req_key, &req_val) && AS_BOOL(req_val)) {
```

If the user puts `required: 1` (an integer) or `required: "yes"` (a string) in the rules map, `AS_BOOL` will reinterpret the raw bits as a boolean. The test suite always uses `BOOL_VAL(true)`, masking the issue. Fix: `IS_BOOL(req_val) && AS_BOOL(req_val)` or a truthiness helper.

## Session secret not zeroed on free

```c
if (session_secret) free(session_secret);
session_secret = (char*)malloc(secret->length);
memcpy(session_secret, secret->data, secret->length);
```

The old key bytes remain in the freed heap block until the allocator reuses that memory. In a long-running server, this leaves key material accessible to memory-disclosure bugs or core dumps. A `memset(session_secret, 0, session_secret_len)` before `free` mitigates this.

## Test coverage gaps

Not tested: session decode with a tampered signature (only tested through the roundtrip), form parse with malformed percent-encoding (e.g., `%GG`), builder stack overflow (depth > 32), pages.scan with non-existent directory, pages.scan with compile errors in `.ve` files, the `db.transaction` rollback path when the closure raises an error.
