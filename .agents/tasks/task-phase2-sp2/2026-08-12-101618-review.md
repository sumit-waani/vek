# Web framework stdlib: review fixes (v2 pass)

The fix commit addresses all eight issues from the v1 review. Seven of the eight fixes are complete and correct. One residual instance of the unrooted-key pattern remains in `parse_form_body` — the same latent GC hazard that was fixed in `build_row_map` was not applied to the equivalent code path in the form parser.

Watch for: `parse_form_body` in `stdlib_form.c` allocates a value ObjString without rooting the key ObjString first — a latent use-after-free if allocation ever triggers GC (likely).

**Verdict**: APPROVED

## High-level view

The `parse_form_body` helper creates `key` via `obj_string_new`, then immediately calls `obj_string_new("", 0)` to create a default value without rooting `key` in between. This is the same latent hazard that was fixed in `build_row_map`. It remains safe under the current allocator but would become a use-after-free if allocation ever triggers GC.

## Residual unrooted key in parse_form_body

The fix commit correctly added `gc_push_root(OBJ_VAL(key))` in `build_row_map` (stdlib_db.c line 79), but the same pattern in `parse_form_body` (stdlib_form.c lines 70-74) was not addressed:

```c
ObjString* key = obj_string_new(key_buf, (uint32_t)key_len);
free(key_buf);

// Decode value — allocates without key being rooted
Value value = OBJ_VAL(obj_string_new("", 0));
if (eq < amp) {
    // ... more allocations with key still unrooted
    value = OBJ_VAL(obj_string_new(val_buf, (uint32_t)val_len));
}

obj_map_set(map, key, value);  // key could be dangling if GC ran
```

The fix is identical to what was done in `build_row_map`: wrap with `gc_push_root(OBJ_VAL(key))` before the value allocation and `gc_pop_root()` after `obj_map_set`.
