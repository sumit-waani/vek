# Epoll-based HTTP server runtime for the vek language (v3)

Third and final review pass. All ten prior issues (7 from v1, 3 from v2) were fixed. Two new concerns emerged: `HttpConnState` leaks on every non-graceful connection close (timeout, EOF, read error), and `http_response_send` triggers a use-after-free when `on_write_done` fires synchronously between the header write and body write for `Connection: close` requests. The "double free or corruption (fasttop)" message at the end of `make test_web_app` confirms heap corruption from these paths. Watch for: use-after-free in two-part response send on non-keep-alive connections (confirmed), HttpConnState leak on timeout and peer disconnect (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The response send path calls `event_loop_conn_write` twice (header then body). If the header write completes synchronously and `keep_alive` is false, `on_write_done_vek` fires immediately, frees the `HttpConnState`, and calls `event_loop_conn_close` which frees the `Connection`. Execution returns to `http_response_send` which then calls `event_loop_conn_write` on the freed pointer. This manifests as the "double free or corruption" observed in test output during shutdown.

The event loop correctly treats `conn->userdata` as opaque and never frees it, but the HTTP layer fails to free `HttpConnState` before invoking `event_loop_conn_close` in the timeout, EOF, and read-error paths. Every timed-out connection and every client that disconnects without sending `Connection: close` leaks a `HttpConnState` (24 bytes + timer pointer).

## Use-after-free: synchronous on_write_done during http_response_send

`http_response_send` issues two sequential writes:

```c
event_loop_conn_write(&server->loop, conn, hdr_buf, (size_t)hdr_len);
free(hdr_buf);

if (body && body_len > 0) {
    event_loop_conn_write(&server->loop, conn, body, body_len);
}
```

Inside `event_loop_conn_write`, a synchronous completion triggers:

```c
if (conn->write_offset >= conn->write_buf.len) {
    conn->write_buf.len = 0;
    conn->write_offset = 0;
    conn->state = CONN_READING;
    if (conn->on_write_done) {
        conn->on_write_done(loop, conn, conn->userdata);
    }
    return true;
}
```

For non-keep-alive requests, `on_write_done_vek` frees state and calls `event_loop_conn_close(loop, conn)`, which frees the Connection struct. Control returns to `http_response_send`, which then calls `event_loop_conn_write` on a dangling pointer. On small responses over localhost (the typical test scenario), the header fits in one `write()` syscall, so this path triggers consistently — producing the "double free or corruption (fasttop)" observed at test shutdown.

The same structural issue exists in `http_server.c`'s `on_write_done` for the non-vek path.

Fix approaches:
- Concatenate header and body into a single buffer and issue one `event_loop_conn_write` call. This eliminates the mid-response callback.
- Alternatively, defer `on_write_done` semantics: don't call `on_write_done` from within `event_loop_conn_write` at all — only call it from `handle_write` in the event loop (i.e., never during the synchronous fast path). The synchronous path would just return true without triggering the callback.

## HttpConnState leak on non-graceful close

`on_timeout_vek`:

```c
static void on_timeout_vek(EventLoop* loop, void* userdata) {
    Connection* conn = (Connection*)userdata;
    ...
    HttpConnState* state = (HttpConnState*)conn->userdata;
    if (state) {
        state->timeout = NULL;
    }
    event_loop_conn_close(loop, conn);  // state never freed
}
```

`event_loop_conn_close` frees the Connection but has no knowledge of the HTTP-layer state. Similarly, when `handle_read` detects EOF or a read error, it calls `event_loop_conn_close` directly — the `on_data` callback is invoked for EOF but not for buffer failure or read error. In neither case is `conn->userdata` freed.

The same pattern exists in `http_server.c`'s `on_request_timeout`.

Fix: free `conn->userdata` before every direct call to `event_loop_conn_close` in both timeout handlers. For the EOF/error paths in `handle_read`, consider adding an `on_close` callback to Connection that the HTTP layer can set to perform cleanup.
