# Epoll-based HTTP server runtime for the vek language

This change adds a full HTTP server stack to the vek interpreter: an epoll event loop, a zero-copy HTTP/1.1 parser, a trie-based URL router with dynamic segments, and native stdlib bindings that let vek scripts register route handlers and run a server. Alongside this, ten stdlib packages (log, env, json, time, crypto, path, uuid, kv, cache, server) are registered as global ObjMaps, making them accessible as `pkg.method(args)` from vek code. The compiler is patched to allow keywords like `get`, `post`, `delete` after the dot operator so `server.get(...)` parses correctly. Watch for: unbounded request body allocation (confirmed), EpollData leak on EPOLL_CTL_MOD (confirmed), no connection-count limit enabling fd exhaustion (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The event loop is a textbook edge-triggered epoll design — single-threaded, non-blocking accept/read/write with timerfd for one-shot timeouts. The HTTP server layer bolts on top by installing accept/data/write-done callbacks that feed data to the parser.

The HTTP parser is zero-copy against the connection's read buffer, scanning for CRLFCRLF to delimit headers and Content-Length to consume the body. It has no upper bound on `content_length`, meaning a malicious client can force arbitrary memory allocation by sending a large Content-Length value that the buffer machinery will attempt to satisfy.

The router uses a trie where each node is a path segment; `:param` segments capture values during recursive matching with literal children tried first.

The VM integration relies on a global `HttpServer` instance. When a request matches a route, the server calls `vm_call` to re-enter the interpreter and execute the vek closure. GC safety is maintained by pinning route closures and pushing temporary objects as GC roots. Any runtime error in the handler sends a misleading empty 200 rather than a 500, and potentially leaves the VM in an inconsistent state for subsequent requests.

<summary>Issues (7)</summary>

1. **Unbounded Content-Length allocation** — The HTTP parser trusts Content-Length without limit. A client can claim a multi-GB body and the event loop's `buffer_ensure` will attempt to `realloc` to match. Add a `MAX_BODY_SIZE` constant (e.g. 1 MB) and reject requests exceeding it with 413. (confirmed)
2. **EpollData leak on partial writes** — `event_loop_conn_write` allocates a new `EpollData` on every `EPOLL_CTL_MOD` for EPOLLOUT interest. The previous EpollData pointer is orphaned. Store the EpollData pointer on the Connection struct and reuse it. (confirmed)
3. **No max-connections limit** — The event loop accepts unbounded connections. Under fd exhaustion the `accept` call returns EMFILE and the loop spins on edge-triggered EPOLLIN. Add a connection cap or handle EMFILE explicitly. (likely)
4. **Handler crash leaves connection dangling** — If `vm_call` triggers a runtime error in a route handler, `vek_http_handler` returns a 200 with empty body instead of 500. Check `vm.had_error` after `vm_call` and send a 500. (confirmed)
5. **No request timeout** — Slow-read attacks (Slowloris) can hold connections indefinitely since there is no per-connection read deadline. Add a timerfd per connection that closes it if a complete request hasn't arrived within N seconds. (confirmed)
6. **Header buffer fixed at 256 bytes** — In `build_request_map`, header names are copied into a 256-byte stack buffer. Names longer than 255 bytes are silently truncated, which could cause subtle lookup failures. (confirmed)
7. **Compiler keyword allowlist is fragile** — `is_identifier_like` uses a manual enumeration of all keyword token types. Adding a new keyword requires remembering to update this function with no compile-time enforcement. Consider a range check or `TOKEN_IS_KEYWORD` macro. (likely)

## Unbounded body allocation and Slowloris surface

The HTTP parser trusts the `Content-Length` header verbatim:

```c
req->content_length = req->content_length * 10 +
                      (size_t)(h->value[j] - '0');
```

There is no cap. When the body hasn't fully arrived, the parser returns `HTTP_PARSE_INCOMPLETE` and the event loop calls `buffer_ensure` on the next read, growing the buffer toward the claimed length. A client sending `Content-Length: 2147483648` with a trickle of actual bytes will cause the server to allocate 2 GB, or fail on `realloc` and close the connection — but not before consuming significant memory. Since the event loop is single-threaded and single-process, this trivially DoS-es the entire server.

There is no per-connection timeout. A client that opens a TCP connection and sends one byte per second never triggers a complete parse, never gets closed, and holds an fd and buffer indefinitely. The combination of no body cap and no read timeout is the primary attack surface.

## EpollData ownership and leak on partial write

The event loop tags each fd's epoll registration with a heap-allocated `EpollData*`, allocated at accept time:

```c
EpollData* ed = epoll_data_new(TAG_CONNECTION, conn);
...
epoll_ctl(loop->epoll_fd, EPOLL_CTL_ADD, client_fd, &ev);
```

When `event_loop_conn_write` can't complete synchronously it needs to add `EPOLLOUT` interest via `EPOLL_CTL_MOD`. But it has no reference to the original `EpollData*`, so it allocates a new one:

```c
EpollData* ed = epoll_data_new(TAG_CONNECTION, conn);
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLOUT | EPOLLET;
ev.data.ptr = ed;
epoll_ctl(loop->epoll_fd, EPOLL_CTL_MOD, conn->fd, &ev);
```

The previous `EpollData*` is now unreachable — a leak on every partial write. When the write completes and `handle_write` does another MOD back to `EPOLLIN`-only, it uses the `ed` passed from the event dispatch (the new allocation), but the old one remains leaked. The fix is to store `EpollData*` on the `Connection` struct (allocated once at accept time, reused across all MODs).

Separately, in `event_loop_run`, connections that receive `EPOLLERR|EPOLLHUP` free their `ed` and close the connection, but listener-tag `EpollData` is never freed during `event_loop_destroy`.

## Handler error propagation gap

When `vek_http_handler` calls `vm_call(entry->closure, 1)`, any runtime error causes `vm_call` to return `VAL_NIL`. The handler then falls through both `IS_STRING` and `IS_MAP` checks into:

```c
} else {
    // Nil or other: send empty 200
    http_response_send(server, conn, 200, "OK", "text/plain", "", 0, keep_alive);
}
```

A 200 response for a server-side error is misleading to clients. The handler should check `vm.had_error` after `vm_call` and return 500. More critically, if a runtime error corrupts the VM's stack or frame state, the event loop continues dispatching subsequent requests using a potentially inconsistent VM — there's no stack-frame cleanup or VM reset after a failed handler invocation.

## Connection count and fd exhaustion

The event loop has no cap on `conn_count`. Under load, connections accumulate until the process hits its fd limit. At that point `accept` returns `EMFILE`. Because the listener uses edge-triggered epoll, a single failed accept leaves the EPOLLIN event consumed — no further accepts are attempted until a new connection arrives and re-triggers the edge. The loop effectively deadlocks on accepts while existing connections continue.

Mitigation: stop accepting when `conn_count` exceeds a threshold, or handle `EMFILE` by temporarily disabling the listener.

## Compiler dot-operator keyword resolution

`is_identifier_like` in `compiler.c` explicitly enumerates every keyword token allowed after `.`:

```c
static bool is_identifier_like(TokenType type) {
    return type == TOKEN_IDENTIFIER ||
           type == TOKEN_GET || type == TOKEN_POST ||
           type == TOKEN_PUT || type == TOKEN_PATCH ||
           type == TOKEN_DELETE || type == TOKEN_IN ||
           ...
```

Any future keyword added to the lexer that's also a valid method name will fail to parse in `obj.keyword()` calls unless this function is manually updated. A token-type range check or flag on the enum would prevent this class of regression.

## Test coverage gaps

Not tested: malformed HTTP requests beyond basic 400 (truncated headers, invalid Content-Length, binary garbage), request body larger than available memory, concurrent connections exceeding fd limits, handler runtime errors returning 500, partial writes that require EPOLLOUT, timer cancellation, and the SIGINT graceful shutdown path.
